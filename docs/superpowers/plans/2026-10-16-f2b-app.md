# F2b — Online in the app: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (Adaam chose inline execution with checkpoints). Steps use `- [ ]`.

**Goal:** play online from the app against a real person, robust to bad mobile networks.

**Architecture:** one thin `OnlineApi` interface over Supabase (Edge Functions, RPCs, table reads, Realtime); everything above it is plain Dart + Riverpod, tested with a fake API. The online game notifier owns optimistic moves, retries with one `client_move_id` per attempt, and resync (server always wins). Clocks are computed from the server row plus a server-time offset.

**Tech stack:** supabase_flutter 2.18.3 (gotrue 2.27.3: `signInWithPassword`/`signInWithIdToken` return `AuthResponse`), google_sign_in 7.2.0 (`GoogleSignIn.instance.initialize(serverClientId:)`, `authenticate()`, `account.authentication.idToken`), app_links 7.2.2, uuid 4.6.0, existing dartchess/chessground/Riverpod/go_router.

**Spec:** `docs/prompts/F2b_app.md`; contract `docs/ONLINE.md` (wins on conflicts); ADR-0004, ADR-0005, ADR-0007.

## Global constraints
- Client never writes tables; mutations only via `make_move`, the RPCs, `delete_account`.
- Supabase project **skak** (`ivznhyyaswhnpdrnnbno`) only.
- Config from `--dart-define-from-file=env/dev.json`: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, optional `GOOGLE_WEB_CLIENT_ID`. Missing URL/key → the app runs offline only and "Play online" explains it.
- Offline play works with no account and no network (Supabase init must never block or crash `main()`).
- UI uses Songket tokens/components only; 360 dp widget test per new screen; action-named buttons.
- Files ≤ ~300 lines, one widget/screen per file.

## Decisions
- **Server time:** `ServerClock.offset` updated from `server_now` (make_move, ms precision) and from the HTTP `Date` header of every Supabase response (1 s precision; used as `date + 500 ms` and only when no make_move sample in the last 60 s). A small `http.BaseClient` wrapper records it.
- **Retry:** network error / 5xx → same `client_move_id`, delays 0.5, 1, 2, 4 s (5 tries total), then resync (the move may have landed). 4xx or `applied:false` → resync + roll back + message.
- **Resync:** fetch `games` row + `moves` with `ply > lastKnownPly`; if the server game's ply is lower than ours (rolled back), or a fetched move doesn't chain, refetch all moves. Rebuild positions from the server moves with dartchess.
- **Rematch** needs a backend change (a waiting invite is visible only to its creator): migration `offer_rematch(p_game)`: on a finished game, if the opponent already offered → `join_invite(their code)`; else `create_invite` with the same time control and store `rematch_code`/`rematch_by` on the old game (Realtime hint reaches the opponent). Adaam pushes it (`npx supabase db push`).
- **History:** DB v3 adds `opponent TEXT` (null = bot game) and `rating_change INTEGER` to the local `games` table; online games use `bot_level = 0`. `Termination.agreement` added. Finished online games are saved when the game ends on this device and synced from the server (last 50) when History opens while signed in. Review works unchanged (reads local PGN).
- **Deep links:** `skak://join/CODE` via app_links; Flutter's built-in deep linking off (`flutter_deeplinking_enabled=false`), so go_router never sees raw custom-scheme URIs.

## Review focus
1. Move made while offline, delivered after 20 s → exactly one row in `moves` (retry reuses the id; after max tries a resync finds it). Test: fake API fails 4× then applies; and "fails 5×, server has it" → resync shows it, no second send.
2. Two quick taps / a hint arriving during a send → no second `make_move` for the same ply, no flicker back. Test: second move ignored while a send is pending; hint-triggered resync during send keeps the optimistic move until the send resolves.
3. Server rejects (STALE/ILLEGAL/GAME_OVER) → board equals server, short message. Test per code.
4. App resumed after 60 s → resync + clocks from `last_move_at`. Test: clock math with offset; resume triggers fetch.
5. Opponent's clock reaches 0 → one `claim_timeout` call, not one per frame. Test.
